# AGENTS.md — frog's eye

frog's eye is a standalone, project-independent host-observability digest: a single Vector instance captures the whole host (logs, container stdout, host/GPU metrics) and a compacting LLM condenses it into a multi-resolution digest. This file is the delegation protocol for the agent maintaining it — extracted from the `bump-java-version` project, which now merely feeds and consumes it.

1. **Problem (writing this file):** keep AGENTS.md compact and outcome-named.
   - **Value:** compact, outcome-named files force the agent to re-derive the *how* each iteration from its tools; without this discipline the file rots as the domain shifts and the agent over-fits to one iteration's specifics.
   - **Contract and constraints:** A problem is a self-amplifying attractor — one autonomous concern with a single extremum (its Reward) and a single trigger (its Attention mechanism) that pulls the agent's attention and amplifies until satisfied. Each is a concern the operator has offloaded to the agent (the agent watches, triggers, and drives it), making this file a delegation protocol, not a checklist. Only one problem is in foreground at a time (Ukhtomsky); before every action the agent verifies exactly one is dominant — concurrent problems signal confusion to resolve first. Control passes when a stronger trigger fires or the current extremum is approached; an interrupted problem is resumed, not restarted, so each persists enough state for resumption to be genuine. Problems are written for an intelligent agent searching a fuzzy environment with the available tooling: supply no implementation detail the agent can fill itself, and — since humans reread this file often — keep each as short as possible. Every problem has five sections: **Value** (why it exists — would the project notice its removal?); **Contract and constraints** (the operator-only boundary the other sections optimize within — the agent does not edit it); **Solution search approach and hints** (what observed failures taught the agent to try first, plus this agent's own loop or trigger for returning to the problem); **Reward** (one extremum the operator reads off without judgement — a count, fraction, or comparable artefact); **Attention mechanism** (how a change this problem makes or notices in the shared environment becomes salient — the channel it publishes a signal to or watches, e.g. a log line, a metric, or an observability stream — as distinct from the agent's own re-entry loop). The one-liner names what the problem produces, not how. Backtick-pinned concretes (paths, command shapes, file and element names) are recognition scaffolding and survive trims; aging enumerations (versions, models) get stripped. This file is small: the meta problem (P1) and the observability problem (P2).
   - **Solution search approach and hints:** read → why → intent — for each clause ask "why is this here?". Strip when the answer is mechanism the agent already fills, a bare plea for the rule, or an aged enumeration; keep when it scopes when the rule applies, names a recognition concrete, or signals when to revisit. Re-run every editing pass; additionally, whenever the operator touches a problem's Contract and constraints, the next pass re-audits that problem's agent-mutable sections.
   - **Reward:** cuts that lose words without losing the rule or its scope; after the pass, every problem's Reward names something the operator can read off without judgement.
   - **Attention mechanism:** the file is the channel — an operator edit to a problem's Contract, or a problem's agent-mutable sections visibly bloating, is the signal that pulls this meta-problem to re-audit that problem.

2. **Problem (frog's eye — compact observations):** everything on the host writes to `/var/log`; Vector ships the tree to a compacting model that condenses it into the orchestrator-visible digest.
   - **Value:** raw observation streams exceed the orchestrator's context budget; without a faithful digest, decisions are made from the wrong fraction of the data and trust in the digest erodes silently.
   - **Contract and constraints:** capture is file-glob based, auto-discovering — no per-source or per-container wiring. A single Vector instance (`obs-vector`) globs two trees: **`/var/log/**/*`** (host system logs + project process logs, written under `/var/log`, e.g. `/var/log/observe/app/`, never `/tmp` scratch) and **`/var/lib/docker/containers/**/*-json.log`** (every container's stdout via the json-file driver — new containers appear as new files automatically, no daemon change and no Docker API dependency; the json envelope is unwrapped to the bare message). Plus two host-resource streams: Vector's `host_metrics` (CPU/mem/disk/load) and a GPU sampler (`nvidia-smi` → `/var/log/observe/app/gpu.log`, picked up by the same glob). Vector ships all of it to the compacting model — Qwen 3.6 **35B-A3B AWQ** (a 4-bit MoE, ~3B active/35B total — chosen over the dense 27B for far higher condense throughput) via the compacting-LLM endpoint (`OBSERVABILITY_COMPACTOR_BASE_URL` in `.env`, currently the AWQ route `…/qwen-3.6-35b-a3b-awq/v1`) with `chat_template_kwargs.enable_thinking: false` (thinking starves the summary — it spends the whole token budget reasoning and emits an empty digest, validated empirically; context budget = that endpoint's `max-model-len`, currently 64K; input over budget is chunked and merged, never truncated). **Repetitions are collapsed before the model** — events are grouped by a signature (stream + source + message with numbers/ids/timestamps masked) and each group is sent once as an exemplar + a count, so a high-frequency repetition (container/veth churn, recurring warnings) condenses ~100× instead of being re-sent line-by-line. This collapse is what keeps the condense rate ahead of a high-volume firehose; without it the model drowns re-reading identical lines. The compactor writes the orchestrator-visible digest. The digest is **multi-resolution** — the compactor presents several time windows (short to long, e.g. seconds to tens of minutes) side-by-side so an anomaly shows by window-to-window contrast, not by absolute level. Capture is continuous (runs whether or not anyone is reading it) and **never content-filtered or throttled**: noise is fixed at its source (a crash-looping unit is stopped, not excluded from the stream) so the digest reflects ground truth; only unreadable files are skipped (binaries, compressed/rotated logs, the journal binary dir). Nothing Vector or the compactor writes may land inside the watched tree (no self-ingest). Every log and spool is size-bounded so a full disk cannot silently stall the digest; both the capture layer and the compactor self-heal (auto-restart). The compactor is never load-bearing for an irreversible decision without a spot-check against the raw `/var/log`. Any consumer's execution whose run window overlaps a gap in capture is invalid.
   - **Solution search approach and hints:** Vector is the canonical capture layer (`obs-vector` container; config versioned in this repo as `vector.toml`, never `/tmp`). Container logs are captured by globbing the json-file driver's files (`/var/lib/docker/containers/**/*-json.log`, mounted read-only into `obs-vector`) — file-based, so every container is auto-discovered with no API dependency and no daemon log-driver change (the `syslog` driver was rejected: it would break the `docker logs` API and rate-limit under load; keep `json-file` + its `log-opts` rotation). Add a new stream by writing it to a file under one of the globbed trees, not by extending the compactor. The multi-resolution digest is a **three-layer rolling fold** — `fast` folds collapsed `/var/log` events, `medium` folds the `fast` digest, `slow` folds the `medium` digest — each emitting its own JSON digest (`{summary, anomalies:[{what,kind,n,distinct,span,last,params:[{what,n,when}]}]}`) to `~/observe/{fast,medium,slow}.jsonl`, **outside the watched tree** so the compactor never self-ingests. Cadence is data-driven, not wall-clock: `medium` folds every `MED_EVERY` fast folds, `slow` every `SLOW_EVERY` medium. The model only folds prior+new and never re-transcribes — exact counts/spans/`params` come from the collapse, and replies are parsed with a string-aware JSON reader (`raw_decode`) so braces inside verbatim log lines don't break extraction; the rolling states persist (`~/.compactor.state`) so a restart resumes the fold. `OUTPUT_BUDGET` (max_tokens) need only be a few hundred — the digest is terse by design (~60–100 tokens); the heavy lifting is the input-side collapse, not the output size. Emit only when state changes materially since the last digest (a quiet stream stays quiet); surface failure signals, not just happy-path; on input over budget chunk-and-merge rather than drop; periodically spot-sample raw vs digest to recalibrate trust. Re-enter whenever a new noisy source appears or the digest goes stale.
   - **Reward:** the **condensation ratio** — raw events in : distinct/anomalous entries out — at a near-zero miss rate. The binding metric is the *condense rate* (distinct signal the model must absorb per second), **not** raw inflow: because repetition collapses to an exemplar + count, a high-volume but repetitive firehose (hundreds× ratio) is cheap, while novel/anomalous signal is always carried. The eye falls behind only when distinct signal — not volume — outruns the model; if it lags, raise the ratio (collapse harder / fix the noise source), don't just demand a faster model. Quiet and repetitive streams stay quiet so emitted entries carry signal.
   - **Attention mechanism:** the digest is the channel — a materially new pattern in the `/var/log` stream (a new error signature, a build or inference failure, a throughput stall, a hardware/OOM/Xid event, a bail label) becomes salient by contrast across the digest's time windows (short to long) and against the prior digest, and is emitted; steady state stays silent. If a source that matters is not writing into `/var/log`, the frog's eye is blind to it — the fix is always to point that source at `/var/log`, never to special-case it in the compactor.
