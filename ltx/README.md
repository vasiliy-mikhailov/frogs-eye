# ltx — LTX-2.5 video generation behind the gateway

Lightricks LTX-2.5 (22B distilled DiT, video + audio) runs on the RTX 4090 eGPU of the Strix Halo box (Windows,
Docker Desktop with the WSL2 GPU). It is published through the same front door as the text models as an
OpenAI-style **async videos API**:

```
https://inference.mikhailov.tech/ltx-2.5/v1/videos
  → Caddy  handle /ltx-2.5/*
  → meterproxy  route /ltx-2.5 (prefix stripped)
  → LiteLLM  openai/ltx-2.5, mode video_generation
  → inference-halo-video  (autossh tunnel container on mh, -L 8101 → Halo 127.0.0.1:8101)
  → ltx_video_adapter.py  (this directory, inside the ltx container)
  → ComfyUI v0.45.0 + ComfyUI-GGUF  (same container, 127.0.0.1:8188)
```

This directory mirrors `C:\ltx\build` on the Halo. `adapter/` is mounted read-only into the container at
`/opt/adapter`, and `image/` is what the image is built from.

| file | role |
|---|---|
| `adapter/ltx_video_adapter.py` | The API: `POST /v1/videos`, `GET /v1/videos/{id}`, `GET /v1/videos/{id}/content`, `GET /v1/models`, plus `GET /health` without auth (its `started` field is the adapter's start time). |
| `adapter/run.sh` | Container entrypoint. It starts ComfyUI (`$COMFY_EXTRA_ARGS`, set to `--disable-metadata` in the env file), waits for it, then starts the adapter. If either process exits, the container exits and Docker's restart policy brings both back. |
| `adapter/ltx25_distilled_gguf_{t2v,i2v,ext}_api.json` | The ComfyUI API graphs the adapter fills: text-to-video, image-to-video, and extend. Generated by `build_workflows.py`. |
| `build_workflows.py` | Rebuilds the three graphs (adapted from Comfy-Org/workflow_templates, MIT), checks every link, and writes them into `adapter/`. It reproduces the deployed files byte for byte. |
| `ext_test.py` | Extension experiment through raw ComfyUI: continues a clip, stitches it, and measures the seam (overlap fidelity, frame-to-frame jump, audio level). |
| `image/setup.sh`, `image/commit.ps1` | Build of the `ltx-comfy:v0.45.0` image, described below. |
| `image/entrypoint.sh`, `image/extra_model_paths.yaml` | Baked into the image: a ComfyUI-only entrypoint (overridden by `run.sh`) and the `/models` layout. |
| `ltx_dl.py` | Downloads model files into the `ltx-models` volume and checks each against its Hugging Face sha256. |
| `start-ltx.ps1` | Recreates the `ltx` container and waits for `/health`. |
| `adapter_test.py`, `run-test.ps1` | Local API test suite on the Halo, described below. |
| `gateway_test.py` | End-to-end test through the public URL with the OpenAI SDK. |
| `dsh-skill/` | The `ltx-video` skill and a dsh plugin tool, so agents (dsh-web, the Mac app, Kimi) can make videos on request. See its README. |
| `render.ps1`, `render_test.py` | Raw ComfyUI benchmark (bypasses the adapter) that samples GPU memory, utilization and power. |

## Image

Docker Hub pulls stall on the Halo (93 MB of 3.15 GB in an hour), so the image is built from the local `python:3.12`
with pip, then committed:

```powershell
docker run -d --name ltx-setup -v C:\ltx\build\image:/b:ro python:3.12 bash /b/setup.sh
docker logs -f ltx-setup        # ends with "SETUP-OK comfy 989d93d0d968"
powershell -File C:\ltx\build\image\commit.ps1
```

`setup.sh` installs:
- torch 2.14.1+cu130 from download.pytorch.org;
- ComfyUI `v0.45.0`, with its requirements minus torch, and it fails if torch was replaced;
- ComfyUI-GGUF `6ea2651e7d`.

`commit.ps1` turns the container into `ltx-comfy:v0.45.0` (about 13.9 GB). It first commits a candidate tag. It moves
the production tag only if `ltx-setup` exited 0 and the candidate passes a check: torch sees the GPU, and ComfyUI-GGUF
is present. Otherwise the production tag is untouched and `ltx-setup` is kept for its logs. The deployed container
never uses the image entrypoint, because `start-ltx.ps1` overrides it with `run.sh`.

There are three traps on the Halo:
- `docker build` and `docker pull` over SSH fail with "A specified logon session does not exist". Docker Desktop's
  credential helper needs the interactive session.
- PowerShell 5.1 strips bare inner double quotes from native arguments. Use `\"`, or put the command in a script file
  (`render.ps1` passes its prompt through an environment variable for this reason).
- The bash scripts must keep LF line endings: a CRLF `run.sh` crash-loops the container and a CRLF `setup.sh` fails on
  line 3. Git for Windows checks out CRLF by default, so `ltx/.gitattributes` pins `*.sh` to LF.

The ungated mirror `comfyicu/LTX-2.5` carries a **stale** text encoder: Lightricks updated it on 2026-10-11. Take the
text encoder from the gated repo with your own Hugging Face login. The login is stored in the `ltx-hf` volume and is
never passed on the command line:

```powershell
docker run --name hfprep python:3.12 pip install -q --root-user-action=ignore huggingface_hub
docker commit hfprep hf-cli:local; docker rm hfprep
docker run -it --rm -v ltx-hf:/root/.cache/huggingface hf-cli:local hf auth login
docker run -d --name ltx-dl -e HF_TOKEN_PATH=/hf/token -v ltx-models:/models -v ltx-hf:/hf:ro -v C:\ltx\build:/build:ro hf-cli:local `
  python /build/ltx_dl.py Lightricks/LTX-2.5:text_encoders/gemma4-12b-with-proj-ltx-2.5-comfy-int8-convrot.safetensors:text_encoders
```

Each `ltx_dl.py` argument is `repo:path-in-repo:subdir`. Progress and the sha256 verdicts go to
`/models/_dl_status.txt`. A file that already exists with the right size and sha256 is skipped.

## Deploy

The engine key goes in `%USERPROFILE%\.ltx\engine.env`. Keep that file out of every repo:

```
LTX_ENGINE_KEY=<64 hex chars, e.g. openssl rand -hex 32>
COMFY_EXTRA_ARGS=--disable-metadata
```

Then run `powershell -ExecutionPolicy Bypass -File C:\ltx\build\start-ltx.ps1`. It recreates `ltx` with:
- `--gpus all --restart unless-stopped`;
- ports `127.0.0.1:8188` (ComfyUI) and `127.0.0.1:8101` (adapter);
- volumes `ltx-models` and `ltx-data`;
- `adapter/` mounted at `/opt/adapter:ro`.

It then waits until the adapter reports healthy. The adapter refuses to start without `LTX_ENGINE_KEY` (unless
`LTX_ALLOW_NO_AUTH=1`) and with an `LTX_MODEL_ID` that cannot be used in URLs.

The box has no auto-logon. After a reboot the service stays down until someone logs in and Docker Desktop starts.

## Gateway wiring on mh

On mh:
1. **Tunnel.** This is a copy of `inference-halo-qwen` with one forward:
   ```bash
   docker run -d --name inference-halo-video --network proxy-net --restart unless-stopped \
     -v ~/.ssh/halo_id:/mnt/halo_id:ro alpine:latest sh -c "apk add --no-cache autossh openssh-client >/dev/null 2>&1; \
     mkdir -p /root/.ssh; cp /mnt/halo_id /root/.ssh/id; chmod 600 /root/.ssh/id; exec autossh -M 0 -N \
     -o StrictHostKeyChecking=accept-new -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
     -o ConnectTimeout=10 -p 22 -i /root/.ssh/id -L 0.0.0.0:8101:127.0.0.1:8101 <user>@<halo-lan-ip>"
   ```
   The listener exists only inside the container on `proxy-net`; mh publishes no port for it.
2. **LiteLLM** (`model_list`, then `docker restart litellm`):
   ```yaml
   - model_name: ltx-2.5
     litellm_params:
       model: openai/ltx-2.5
       api_base: http://inference-halo-video:8101/v1
       api_key: <LTX_ENGINE_KEY>   # without it LiteLLM falls back to OPENAI_API_KEY and sends that over the tunnel
       timeout: 300
     model_info:
       mode: video_generation
       disable_background_health_check: true
   ```
3. **meterproxy** reads `ROUTES` only at startup, so add `"/ltx-2.5": "litellm:4000"` and recreate it. Copy
   `CLIENT_KEYS`/`UPSTREAM_KEY` through a 0600 `--env-file`, never through `-e` arguments.
4. **Caddy:** add `handle /ltx-2.5/* { reverse_proxy meterproxy:8091 }`, then run `caddy reload`.

The model name must agree in four places: LiteLLM `model_name`, the `openai/<name>` suffix, the meterproxy and Caddy
prefix, and the `model` LiteLLM sends. The adapter embeds that `model` in every id it returns.

## API

`POST /v1/videos` takes either JSON or multipart. The SDK always sends multipart to LiteLLM; LiteLLM then sends JSON
upstream, or multipart when there is an image. Fields:

- `prompt` (required). Up to `LTX_MAX_PROMPT_CHARS` (8000).
- `size` `WxH`:
  - each side is floored to a multiple of 64, with a minimum of 256;
  - the aspect ratio must be within 1:3;
  - sizes above 1280×704 are scaled down, keeping the aspect ratio;
  - the default is 1280x704.
- `seconds`:
  - accepted range is (0, 60] seconds;
  - frames are rounded to 8k+1 and capped at `LTX_MAX_FRAMES`, 481 (20 s at 24 fps);
  - the default is 5.
- `input_reference` (image-to-video): a PNG, JPEG or WebP file part, or a `data:` URL in a JSON body. Through LiteLLM,
  a `data:` URL arrives as the text of a file part; the adapter decodes it either way.
  - Limits are 20 MB and 4096×4096.
  - The image is re-encoded to a single-frame PNG before ComfyUI sees it.
- Extra fields, which LiteLLM forwards:
  - `seed`, 0..2^64-1, random by default;
  - `negative_prompt`, up to 2000 characters;
  - `fps`, 8..50, default 24.
  - `extend_from`: a finished video's id, to make it longer (see below).
  - A client that cannot add fields can put `<ltx_args>{"seed": 1}</ltx_args>` in the prompt instead.

**Extend.** With `extend_from`, the prompt says what happens next, and `seconds` is the *new* content: up to 15 s,
default 15. A source shorter than 5 s carries over whole.
- The last `LTX_EXTEND_OVERLAP_FRAMES` (121, 5 s at 24 fps) of the source are cut out with ffmpeg. Only that tail is
  decoded, never the whole video.
- The `ext` graph renders overlap plus new content (20 s at most). The overlap frames are VAE-encoded into the first
  latent frames at both stages and pinned at strength 1.0. The overlap's sound is encoded and pinned at the start of
  the audio stream, and `LTXVConcatAVLatent` zero-pads the rest, unmasked, so the model continues both.
- The overlap is cut off the result. **Only the new frames are encoded.** They use the same x264 settings
  (`stitchable=1`) as everything the adapter writes, and the video joins by stream copy, so earlier footage is never
  re-encoded. Before this, the opening of a long chain lost about 1 dB per hop (28.6 dB PSNR after 60 hops).
- The first hop normalizes a ComfyUI-made source once, because its x264 headers differ from ours.
- The sound lives losslessly in `<id>_audio.flac` next to each output. The seam is crossfaded over 0.1 s with the
  lengths kept exact, so sound never drifts against picture. AAC is encoded once per hop, from the FLAC.
- In a four-hop simulation:
  - frame counts were exact when decoded;
  - sound length matched picture length to within 1 ms;
  - the opening frames were bit-identical across hops.
- The janitor keeps any source that a queued or running extension still needs. The FLAC sidecars count toward
  `LTX_KEEP_GB` and are deleted with their video. A failed extension deletes its overlap cut, segment and sidecar.
- The output is the whole video. Extend its id again to continue, up to `LTX_MAX_TOTAL_S` (900 s).
- Size and fps follow the source. `input_reference` cannot be combined with it.
- Measured on a 20 s clip extended by 15 s:
  - the regenerated overlap differs from the source by about 2/255 per pixel;
  - the frame-to-frame change across the seam is 2.6, against 1.8–2.4 around it;
  - the audio has no click at the seam.

Create returns at once with `queued`. Jobs then go through ComfyUI **one at a time**. At most `LTX_MAX_QUEUE` (3) jobs
can be queued or rendering at once, for example 1 rendering and 2 waiting. The next create gets 429 with
`Retry-After: 30`. The `jobs_waiting` field of `/health` counts the same jobs. Poll `GET /videos/{id}` until the status
is `completed`, then fetch `/content` (`video/mp4`, H.264 + AAC 48 kHz stereo). Outputs are kept `LTX_KEEP_HOURS`
(24 h, shown as `expires_at`) and the store is capped at `LTX_KEEP_GB` (30). After that the job reports `failed` with
`video_expired` (HTTP 200). Job records are dropped 7 days after they finish; after that the id gets
`video_not_found`.

Jobs persist in `/data/adapter/jobs.json`. `run.sh` restarts the whole container when ComfyUI or the adapter exits, and
ComfyUI's queue lives in memory. So after a restart, queued and in-flight jobs are re-queued and rendered from the start
once the models reload. Each ComfyUI `prompt_id` is derived from its job id, which only guards against submitting a job
twice to the same ComfyUI.

A job stays `queued` while ComfyUI runs other work, for example a graph from the node editor. It turns `in_progress`
when ComfyUI starts it, and `LTX_JOB_TIMEOUT_S` counts from then. Polls that keep failing for 120 s count as
"ComfyUI stopped answering". A job that waits behind others longer than
`LTX_QUEUE_WAIT_S` (7200) fails alone; ComfyUI is busy, not stuck.

The adapter fails the job and then exits, so Docker restarts the container and the CUDA context, in three cases:
- a job runs past `LTX_JOB_TIMEOUT_S` (600 s of running, about 3.5× a 20 s render). It is also cancelled in ComfyUI;
- ComfyUI stops answering `/system_stats` for 120 s;
- a render fails with a sticky CUDA error (illegal memory access, launch failure). Out-of-memory errors are not sticky
  and do not trigger a restart.

### Quirks forced by LiteLLM 1.98

These were each verified against a throwaway `ghcr.io/berriai/litellm:v1.98.0`:
- **Ids:** LiteLLM routes status and content calls by a `model_id` encoded inside the video id. The adapter therefore
  returns ids already in LiteLLM's form: `video_` + base64 `litellm:custom_llm_provider:openai;model_id:<model>;video_id:<raw>`.
  If `<model>` does not resolve, LiteLLM sends the call to api.openai.com.
- **Status:** LiteLLM never checks the HTTP status of the status GET. It validates whatever body comes back as a
  VideoObject. Unknown ids therefore get a VideoObject-shaped `failed` body (`video_not_found`) with HTTP 404.
- **Content:** LiteLLM relabels any `/content` body as `200 video/mp4`. For `User-Agent: litellm/*` the adapter drops
  the connection when there is no mp4 (the client sees a 5xx), rather than serving error JSON that would be saved as
  a video.
- **Reconnect retries:** LiteLLM's reconnect retry re-sends a multipart create as urlencoded, without the file part.
  The adapter answers 503, which is retriable.
- **Health probe:** LiteLLM's probe (`prompt == "test video generation"`) is answered from `/health` and renders nothing.
- **Duplicate creates:** an identical create within 30 s returns the existing job instead of queueing a second render.

Known gaps on the LiteLLM side:
- `GET /v1/videos` (list) fails;
- the proxy has no DELETE route;
- `?variant=thumbnail` is not forwarded, so a thumbnail request returns the mp4.

## Tests

- **`run-test.ps1`** runs `adapter_test.py` in a throwaway container sharing `ltx`'s network. It reads the engine env
  file and never prints the key. It has three phases:
  - `main`, 40 checks:
    - auth, 400s for 15 malformed inputs, and 503 for a urlencoded body;
    - the health probe and an unknown id;
    - a valid `data:` URL both as JSON and in LiteLLM's file-part form (both must map to one job, which must render);
    - retry dedupe and the `/content` drop for LiteLLM;
    - a T2V render, with mp4 checks and no workflow metadata in the file;
    - extending it by 2 s, which must give exactly 121 frames with sound as long as the picture;
    - an I2V render;
  - `restart-create`: queue a job, wait until it is in progress, and record the adapter's start time;
  - `restart-check`: run after `docker exec ltx pkill -f ltx_video_adapter.py`, once `docker ps` shows `ltx` up again.
    It waits for `/health`, then checks that the adapter's start time changed, that the T2V job from `main` still
    reports completed and its mp4 downloads, and that the interrupted job was restored, re-queued and completed.
- **`gateway_test.py`** runs through the public URL with the OpenAI SDK.
